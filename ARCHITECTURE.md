## Implemented systems

### Core (`Assets/Scripts/Core/`)

- `GameManager` — singleton, persists across scenes, holds top-level game state (`Boot`, `Playing`, `Paused`, `Cutscene`), exposes `Pause()` / `Resume()`.
- `GameSceneManager` — wraps `UnityEngine.SceneManagement` for scene loads (sync + async), logs scene transitions. Named `GameSceneManager` to avoid colliding with the engine's own `SceneManager`. Exposes a static `IsLoading` (TASK 025) because the things that need to know a load is in flight are not holding a reference to it and must not have to — see `SettingsManager.ApplyDisplaySettings`.
- `SettingsManager` — singleton, holds runtime settings (master volume, mouse sensitivity, invert-Y, difficulty, and SPEC.md section 43's `TextScale`/`SubtitleBackground`/`CameraShakeEnabled`/`ScreenEffectsEnabled`/`AimAssistEnabled`, TASK 017), persists `GameSettings` to `PlayerPrefs` as JSON. Also owns the shared `PlayerControls` `InputActionAsset` reference and loads any remembered rebind overrides onto it in `Awake` (`LoadBindingOverrides`), before any controller reads a binding — `SaveBindingOverrides`/`ResetBindingOverrides` are `RemapUI`'s save/reset buttons. `Apply()` also pushes `MasterVolume` to `AudioListener.volume` — the slider wrote and persisted a value nothing read until TASK 019's audit, harmless while there was no audio and a broken control the moment TASK 018 added some. `ApplyDisplaySettings()` (TASK 025) applies quality level and resolution, and **refuses outright while `GameSceneManager.IsLoading`**, retrying once the load finishes: that is SPEC.md section 54's edge case 20, since resizing the screen underneath a half-built canvas produces a layout measured against a screen that no longer exists. A resolution of 0×0 and a quality level of −1 mean "leave whatever the build is on alone", so a fresh install forces nothing the player never chose.
- `DeviceWatcher` (TASK 025) — SPEC.md section 54's edge cases 21, 22 and 23: a controller disconnecting, one reconnecting, and the window losing focus. Subscribes to `InputSystem.onDeviceChange` and implements `OnApplicationFocus`/`OnApplicationPause`. Asks for a pause by publishing `AutoPauseRequestedEvent` rather than calling `GameManager.Pause` directly, because pausing is two things — the state, which `GameManager` owns, and the panel, which `PauseMenu` owns — and setting the state alone leaves a frozen game with no menu on it, after which the next Pause press would resume without ever having shown one. Nothing here resumes automatically: coming back to a game that un-paused itself mid-swing is worse than one more keypress. `Gamepad.all` is consulted on every device event rather than trusting the event alone, so a player with two pads who unplugs one is not paused. `HandleControllerChanged`/`HandleFocusChanged` are public because neither Unity callback can be raised from a test.
- `EventBus` — static generic publish/subscribe utility (`EventBus.Subscribe<T>`, `EventBus.Publish<T>`) so systems can react to state changes without direct references to each other (SPEC.md section 49).
- `WorldState` — the central world-state model (SPEC.md section 71): named boolean flags plus integer counters, published as `WorldFlagChangedEvent`. Deliberately a flat named store rather than one field per story beat, because dialogue, quests and memories reference flags by name from ScriptableObject data. `WorldFlags` names the flags the engine itself reads. Persists across scene loads.
- `SaveIdentity` — a stable per-object id (SPEC.md TASK 009), for anything whose state should survive a save independently of scene hierarchy or GameObject name. Optional and opt-in.
- `WorldObjectState` — namespaced world flags (`OBJ_DEAD_<id>`, `OBJ_COLLECTED_<id>`) built on `WorldState`, so `EnemyHealth` and `MemoryPickup` can remember "did this happen" through the same mechanism story flags already use, with no change to `SaveData`'s shape.
- `Difficulty` — SPEC.md section 44's four modes and what each one changes: enemy damage, telegraph length, attack cooldown, how many enemies may attack at once, and player timing windows. Static rather than a component because every enemy reads it on every swing and an enemy spawned before a manager's `Awake` must still get a correct answer; `SettingsManager` owns persisting it. There is deliberately **no health multiplier** — SPEC.md sections 15 and 44 require difficulty to move behaviour and timing, not hit points.
- `SceneSingleton` — backs the `Instance` property of the scene-level managers, resolving on first access rather than only in `Awake`. See **Manager lookup** below.
- `GameLogger` — static categorized logging (`[GAME] [PLAYER] [COMBAT] [AI] [QUEST] [DIALOGUE] [MEMORY] [SAVE] [UI] [AUDIO] [PERFORMANCE] [ERROR]`, SPEC.md section 51).

### Player (`Assets/Scripts/Player/`)

- `PlayerController` — `CharacterController`-based movement (move, sprint, jump, gravity), reads input via the Input System through a serialized `InputActionAsset`, looking actions up by name. There is deliberately no generated C# wrapper class for the asset, so the actions can be re-authored in the Editor without a code-gen step. `FacingTarget` makes movement strafe around a transform instead of turning towards the movement direction; it is set by lock-on and the controller does not know why.
- `PlayerCamera` — third-person orbit/follow camera with spherecast-based collision avoidance so it does not clip through geometry (SPEC.md section 38). `LookTarget` frames a transform instead of following the look stick; yaw and pitch are kept current while it is set, so releasing it hands control back without a jump. Look input splits by device (TASK 017): mouse delta is per-frame pixels and multiplies by `sensitivity` directly, a gamepad stick is a -1..1 rate and multiplies by `gamepadLookDegreesPerSecond * Time.deltaTime` instead — the two were sharing one raw multiplier before, which is why gamepad look was far too slow (KNOWN_ISSUES, TASK 001). `Shake` (SPEC.md section 43's camera-shake toggle) adds a decaying random offset in `LateUpdate`, gated by `SettingsManager.Current.CameraShakeEnabled`; a perfect parry and a broken guard trigger it automatically.
- `PlayerProgressionStats` (TASK 016) — applies the skill tree's Guardian/Divine stat bonuses to this player's `HealthComponent`/`DivineEnergyComponent`. Captures each component's base max once at `Awake` and always recomputes "base + current total bonus" from scratch on every `SkillBonusesChangedEvent`, rather than adding deltas incrementally, so a live unlock and a save's restore replaying the same unlocked set can never double-count. Kept out of `HealthComponent`/`DivineEnergyComponent` themselves because those are shared with every enemy, none of which has skills.

### Combat (`Assets/Scripts/Combat/`)

- `DamageData` — the value passed for one damage application: amount, type, source, hit point, direction, and an `AttackId` allocated per swing.
- `HealthComponent` — the single health pool used by the player and every enemy. All damage goes through `TakeDamage`, which is the one place that rejects self-damage, damage to the dead or invulnerable, and repeated attack ids. `SetMaxHealth` (TASK 016) recomputes the cap without healing to it, for `PlayerProgressionStats`'s skill bonuses.
- `StaminaComponent` — pool gating attacks, dodges and blocks, with a regeneration delay after each spend. `Regenerate` takes time as an argument so tests can step it deterministically.
- `DivineEnergyComponent` — the resource divine abilities will spend. Starts empty; a perfect parry fills it, and Ember Step (TASK 011) spends it. `SetMaxEnergy` (TASK 016) is `HealthComponent.SetMaxHealth`'s counterpart for `PlayerProgressionStats`'s Divine skill.
- `Hitbox` — the damaging volume of a swing. Disabled except during an attack's active window; remembers which hurtboxes it touched during the current swing.
- `Hurtbox` — a collider that forwards damage to a `HealthComponent`, with a per-collider multiplier for weak points. Resolves its health pool lazily rather than only in `Awake`.
- `WeaponController` — owns swing timing (windup / active / recovery) for light, heavy and finisher attacks and opens the hitbox for the active window only. Takes a damage multiplier per swing, which is how a completed combo chain reaches the hitbox, and reads the Warrior branch's "attack damage" skill (TASK 016) as a second multiplier alongside it.
- `CombatController` — turns player input into attacks, dodges, guards and the divine ability; owns stamina costs, the combo tracker, the finisher decision and the dodge/ability invulnerability windows. A light attack against an enemy at or below the finisher threshold becomes a finisher. `TryAbility` is Ember Step (SPEC.md section 8.1, TASK 011): a short dash paid for with `DivineEnergyComponent` rather than stamina, on its own cooldown, publishing `EmberStepUsedEvent` so `Memory` can apply the ability's cost without Combat referencing Memory.
- `ComboChain` / `ComboTracker` — SPEC.md section 14's chain table and the matcher over recent inputs. Plain C#, time passed in. The longest chain whose steps are the tail of the recent history wins, so Light→Light→Heavy beats Light→Heavy.
- `GuardController` — block and parry on one input: the press opens a parry window, holding past it is a block. Registers itself as the `HealthComponent.Guard` and gets first look at incoming damage through `IDamageGuard`. Windows scale with `Difficulty.Modifiers.PlayerTimingWindow`.
- `LockOnController` — picks the best hostile in view and points the player (`FacingTarget`) and the camera (`LookTarget`) at it until it dies, leaves range, or the player lets go. Candidates are hurtbox owners not on the player's side, so it knows nothing about AI. SPEC.md section 43's aim/lock-on assistance (TASK 017) widens `acquireHalfAngle` by a fixed multiplier while `SettingsManager.Current.AimAssistEnabled` is on — a wider cone, not a different ranking rule, so assisted and unassisted play pick the same candidate whenever both find one at all.
- `EnemyHealth` — enemy reaction to the shared health pool: hit flash, death cleanup, despawn. With an optional `SaveIdentity`, marks `WorldObjectState.DeadFlag` on death and restores a remembered death directly (SPEC.md TASK 009) rather than replaying `HealthComponent.Kill`, guarded on `IsDead` so an ordinary kill does not re-trigger on its own notification.
- `PlayerDeath` — player reaction to death: disables controls, then respawns at the current checkpoint.
- `Checkpoint` — idempotent respawn point. Only the first activation raises `CheckpointActivatedEvent`. `RestoreActivated` marks it activated without publishing that event, for a save load.
- `CheckpointManager` — singleton holding the current respawn point, so `Checkpoint` and `PlayerDeath` do not have to know about each other. `RestoreActiveCheckpoint(id)` looks a checkpoint up by id and makes it current, for `SaveManager.Apply`.
- `DamageVolume` — hazard trigger that damages what stands in it on a cadence.
- `CombatEvents` — the `EventBus` payloads: `DamageAppliedEvent`, `EntityDiedEvent`, `PlayerDiedEvent`, `PlayerRespawnedEvent`, `CheckpointActivatedEvent`, `ParryEvent`, `AttackBlockedEvent`, `GuardBrokenEvent`, `LockOnChangedEvent`, `ComboPerformedEvent`, `FinisherStartedEvent`, `EmberStepUsedEvent`.

#### How one hit flows

`CombatController` → `WeaponController.TrySwing` → (windup) → `Hitbox.Activate` → trigger or overlap → `Hurtbox.ApplyDamage` → `HealthComponent.TakeDamage` → `EventBus`.

`Faction` on `Hitbox` and `Hurtbox` decides who an attack is willing to hurt. `Neutral` is the default and opts out of the check entirely, so anything authored before factions existed — the player's weapon, the training dummy — behaves exactly as it did. Enemies are `Hostile`, which is what stops two of them swinging at the same player from killing each other.

Duplicate damage is prevented at two levels, because the two failure modes are different. `Hitbox` remembers the hurtboxes it has already touched, which stops repeated trigger callbacks within one swing. `HealthComponent` remembers recent attack ids, which stops two separate hurtboxes on the same entity both landing the same swing.

#### How a hit is answered

`HealthComponent.TakeDamage` consults its `Guard` after registering the attack id and before touching health. The order matters: a parried or blocked swing has its id consumed, so it cannot land later from a second collider once the guard window has closed. `GuardController` decides in this order — environmental damage is never guarded; inside the parry window the hit is parried, once per press; while holding, an unblockable attack breaks the guard and lands, otherwise stamina pays for the block or, if it cannot, the guard breaks and the hit lands. A broken guard is a short stun during which the player can do nothing.

"Successful parry staggers enemy" (SPEC.md section 15) crosses from Combat to AI without a reference: the guard publishes `ParryEvent` naming the attacker, and each `EnemyStagger` checks whether the attacker is itself. Entering the Stagger state cancels the enemy's swing, so a parry stops the attack that was in flight.

### World (`Assets/Scripts/World/`)

- `Interactable` — abstract base for everything the player can press Interact on, with shared flag gates (`requiredFlags` / `blockingFlags`) and a prompt line. NPCs and memory pickups derive from it so `PlayerInteractor` knows exactly one type.
- `PlayerInteractor` — finds the best interactable near the player and runs it. Selection is angle-weighted distance, not nearest-wins, so facing the thing you mean to talk to selects it. Publishes `InteractionTargetChangedEvent` so the prompt UI does no polling.
- `LocationTrigger` — a volume that reports a quest objective and/or sets a flag on entry. It does not know which quest it serves, so one volume can satisfy several.
- `SupernaturalEvent` — the scripted Act I sleep and bleeding-statue sequence (SPEC.md section 68, scenes 5 and 7). Starts when a named flag is set. `ApplyEndStateImmediately` reaches the same end state with no sequence, for loaded saves and tests. Deliberately not a `CinematicPlayer`: SPEC.md section 69 asks for "gameplay storytelling" here, so it plays out around a player who keeps full control, which a cinematic's whole job is to take away.
- `CinematicPlayer`/`CinematicBeat` — the skippable, subtitled cinematic system (SPEC.md section 69, TASK 014): a flat array of `(subtitle, duration)` beats rather than a timeline/track asset, because nothing yet needs camera or actor data — both are natural additions to `CinematicBeat` once a cinematic wants them. `Play` calls `GameManager.EnterCutscene` (freezing `Time.timeScale`, same as `Pause`) and paces its beats on `Time.unscaledDeltaTime` so the freeze it just caused does not also stop it. `Skip` ends it on the spot; `ApplyEndStateImmediately` reaches the same end state with no sequence, the same shape as `SupernaturalEvent`'s method of the same name. Publishes `CinematicStartedEvent` (carrying the player itself, so `CinematicUI` has something to call `Skip` on — every other UI event in the project carries only a payload, but the skip button is inherently "stop that specific sequence"), `CinematicBeatShownEvent` per line, `CinematicSkippedEvent`, and `CinematicCompletedEvent` (`CinematicEvents.cs`).
- `IPuzzleElement` — the reusable puzzle framework's only contract (SPEC.md section 26, TASK 012): `IsSatisfied` plus a `Changed` event. A new puzzle category is a new class implementing this, not a new controller.
- `PuzzleController` — solves the moment every listed element is satisfied at once and stays solved afterwards (matches `Checkpoint`'s activation idempotency). Sets a flag, reports an optional quest objective, publishes `PuzzleSolvedEvent`, and restores from a save the same check-now-and-subscribe way `EnemyHealth`/`MemoryPickup` do (TASK 009).
- `FireBrazier` — the first `IPuzzleElement`: an `Interactable` that lights on interact and burns out on its own after a set duration unless relit. The burn timer is the puzzle's whole logic, and it is directly visible.
- `PuzzleGate` — a blocking collider that opens permanently once its puzzle solves, matched to the controller by an id string through `PuzzleSolvedEvent` rather than a direct reference — the same decoupling `Checkpoint`/`CheckpointManager` use.
- `WorldBounds` (TASK 022) — the volume a scene treats as "inside the world" (SPEC.md section 50's invalid player position, section 54's edge cases 9 and 10, section 56's out-of-bounds traversal): a kill plane plus an optional horizontal footprint. The box's Y extent is deliberately unused — the kill plane is the only vertical limit, so a jump, a staircase or a tall temple can never read as an escape. A scene without one is permissive rather than broken (`IsInsideWorld` answers true), which keeps every test arena working and makes the volume something a level opts into.
- `PlayerBoundsGuard` (TASK 022) — polls the player's position and, when it is outside, teleports them to the latest valid checkpoint (the wording section 50 uses), falling back to the last position they stood on solid ground. Recovery, not death: falling through the floor is a bug in the level, and charging the player whatever death costs for it would be punishing them for someone else's mistake. Clears accumulated fall speed via `PlayerController.CancelVerticalVelocity` — by the time a fall out of the world is noticed the downward velocity is large enough to punch straight back through the floor on the next frame. Publishes `OutOfWorldRecoveryEvent` so `RecoveryMessageUI` can say why the player moved.
- `EnemyBoundsGuard` (TASK 022) — the same for enemies, returning them to their authored home via `NavMeshAgent.Warp` (a plain transform assignment is silently undone by the agent). Put back, never destroyed: an enemy can be a `QuestTarget` or a boss, and section 55 says a required NPC cannot disappear permanently. Silent to the player, who neither caused it nor can act on it, but logged for whoever authored the hole.
- `MemoryToll` — a one-time barrier paid in memory integrity (SPEC.md Phase 3's "memory cost", TASK 015), distinct from Ember Step's per-use drain: a cost of entering a place rather than of using an ability. Never a hard stop — `MemoryManager.ReduceIntegrity` clamps at zero rather than refusing, so paying is always possible regardless of how much integrity is already spent (section 55's anti-softlock rule). Restores from a save the same check-now-and-subscribe way `FireBrazier`/`MemoryPickup` do, via a new `WorldObjectState.PaidFlag`.

### AI (`Assets/Scripts/AI/`)

All ten behaviours SPEC.md section 17 asks for exist as values of `EnemyState`.

- `EnemyArchetype` — one enemy class as data (ScriptableObject): vitals, poise, speeds, leash, perception ranges, attack timings, retreat threshold, placeholder tint. Difficulty is applied when a number is *read* (`TelegraphFor`, `DamageFor`, `CooldownFor`) rather than baked in, so changing difficulty mid-run takes effect on the next swing.
- `EnemyController` — the state machine. It owns transitions and per-state behaviour and nothing else.
- `EnemySenses` — everything the enemy knows on one tick, gathered before any decision.
- `EnemyPerception` — sight cone, hearing radius, line-of-sight raycast, and the last known target position that Chase and Search both steer to.
- `EnemyNavigator` — `NavMeshAgent` movement plus SPEC.md section 50's navigation-failure fallback. Falls back to steering the transform directly when no NavMesh is usable, so an unbaked scene is playable rather than full of frozen enemies.
- `EnemyCombatant` — one attack: telegraph, active window, recovery, cooldown. Drives a `Hitbox` directly rather than reusing `WeaponController`, because enemy timings and damage come from the archetype and are rescaled by difficulty per swing. SPEC.md section 43's "never colour alone" (TASK 017) adds a non-colour cue alongside the existing telegraph tint: a brief uniform scale pulse on the enemy's renderers, applied and cleared in step with the tint so a colourblind player still gets a readable attack warning.
- `EnemyStagger` — poise, hit reactions and knockback. `ForceStagger` is the hook SPEC.md section 15 needs for "successful parry staggers enemy".
- `EnemyGroup` — group coordination: a limited number of attack slots so a mob rotates instead of swinging as one, and a shared alert so a patrol reacts as a squad. Grouping is hierarchy — members find their group with `GetComponentInParent`.
- `PatrolRoute` — waypoints, shared between enemies, drawn as gizmos.
- `AIEvents` — state changed, alerted, staggered, lost target.
- `BossController` — the SPEC.md section 18 boss framework (TASK 013), layered on top of an ordinary `EnemyController`/`EnemyCombatant`/`HealthComponent` rather than a separate creature type: a boss is an enemy with phases. `PhaseFor` is a `static` pure function over a health fraction, in the same shape as `EnemyController.Decide`. Each phase raises `EnemyController.SetSpeedMultiplier`/`EnemyCombatant.SetCooldownMultiplier` rather than damage or max health — section 18's "do not make bosses difficult by only increasing HP" — and phase 3 additionally calls `EnemyController.ApplyPhaseTint` as a placeholder supernatural-transformation cue (section 78). Reveals a `reward` GameObject on death and publishes `BossEncounterStartedEvent`/`BossPhaseChangedEvent`/`BossDefeatedEvent` (`BossEvents.cs`) for the HUD and later systems. `onEncounterStarted`/`onPhase2Entered`/`onPhase3Entered`/`onDefeated` are `UnityEvent` hooks left for the cinematic system (TASK 014) and the VFX/animation pass (TASK 018) to wire real content into, rather than this class growing a direct reference to either. With an optional `SaveIdentity`, a defeat survives a save through the same `WorldObjectState.DeadFlag`/check-now-and-subscribe pattern as `EnemyHealth` — see `MarkDefeated`'s doc comment for the ordering hazard that pattern creates here specifically (a live kill's `Died` handler races its own nested restore path) and how `fanfarePlayed` resolves it. `ResetEncounter()` (TASK 023) abandons a live fight: full health, phase 1, `EncounterStarted` cleared, `EnemyController.ResetToHome()`, and `BossEncounterResetEvent` — a defeated boss is never reset, because death is permanent and saved.
- `BossArena` (TASK 023) — the ground a fight is allowed to happen on (SPEC.md section 54's edge case 7, section 55's "important boss arenas must reset safely", section 56's "boss arena escape"). Walking out neither traps nor kills the player; after a grace period it simply ends the fight and `ResetEncounter`s the boss, so the arena resets safely *and* chipping a boss from outside stops paying, which is the same rule answering both requirements. A radius rather than a trigger volume on purpose: a trigger needs an exit event, and an arena whose reset depends on one fails open in exactly the case that matters — the player leaving by a route the collider does not cover. Asking "where is the player now" cannot miss. The grace period exists because section 56 also says not to over-restrict: a dodge or a knockback across the line must not end the encounter.

**Why the state machine is split this way.** `EnemyController.Decide` is a `static` pure function from `(current state, EnemySenses, archetype, time in state)` to the next state. Seeing, moving, swinging and reeling all live in the other components. That is what makes the rules worth testing — whether an enemy gives up, leashes, retreats or yields its attack slot — testable without a NavMesh, a frame or a physics step. The whole transition table is covered by unit tests; everything below it needed a play-mode run.

### Dialogue (`Assets/Scripts/Dialogue/`)

- `DialogueData` — the serializable pieces: `DialogueNode`, `DialogueChoice`, `DialogueConsequence`, `ConsequenceType`. Field-for-field the shape SPEC.md section 22 recommends.
- `DialogueGraph` — one conversation as a ScriptableObject: a flat list of nodes plus the `NextDialogueId` links between them, so it stays editable in the Inspector without a custom graph editor. `GetEntryNode` picks the first entry whose gates pass, which is how an NPC says something different after the quest is given.
- `DialogueRunner` — walks a graph and applies consequences. Logic only: it holds no UI references and draws nothing, so dialogue can be driven headlessly by tests. A missing graph, or one with no usable entry node, runs a one-line fallback conversation showing SPEC.md section 50's exact `[Dialogue unavailable]` string (TASK 024) — built on a real, code-created `DialogueGraph` rather than threaded through the UI as a special case, so the panel, the advance key and the completion event all behave as they do for authored dialogue and the player dismisses it normally. `Begin` still returns **false** on that path, and that is the point: the caller's own consequences (`NpcInteractable`'s first-spoken flag, and anything a quest hangs off it) must not fire for a conversation that did not happen. A display fallback is not a conversation. A dangling link *mid*-conversation keeps its pre-existing behaviour of ending cleanly — the player has read real lines by then, so ending is honest where an error string would not be.
- `NpcInteractable` — an NPC that hands its graph to the runner. Adding a character is authoring an asset, not writing a script.
- `DialogueEvents` — `DialogueStartedEvent`, `DialogueNodeShownEvent`, `DialogueChoiceMadeEvent`, `DialogueConsequenceEvent`, `DialogueCompletedEvent`.

### Quests (`Assets/Scripts/Quests/`)

- `QuestData` — `QuestObjective`, `ObjectiveType`, `QuestStatus`.
- `QuestDefinition` — a quest as authored content (ScriptableObject, immutable at runtime).
- `QuestProgress` — the player's state within one quest. Kept out of the definition because mutating a ScriptableObject at runtime writes progress into the asset in the Editor.
- `QuestManager` — the only thing that knows a quest's shape. Triggers, NPCs and memory pickups report "objective X happened" by id and this decides whether that advances anything.
- `QuestTarget` — marks an entity as counting towards an objective when it dies, giving `ObjectiveType.DefeatEnemy` a driver. It lives here rather than in `AI` so nothing in `Game.AI` has to know quest ids exist.
- `QuestEvents` — started, objective advanced, objective completed, completed, failed.

### Memory (`Assets/Scripts/Memory/`)

- `MemoryFragment` — one collectible memory (ScriptableObject), with the category, state and importance enums from SPEC.md sections 19 and 21.
- `MemoryManager` — which memories the player has and what state each is in, plus the 0..1 `Integrity` model from SPEC.md section 20. The safety rule is enforced here rather than left to callers: a `Critical` memory cannot be moved to a degraded state, so no ordinary gameplay can make story progression unreachable. `Corrupt` ties state and integrity into one "spend a memory" action (SPEC.md TASK 010), refusing and spending nothing when the target is protected, and reads the Memory branch's "memory manipulation" skill (TASK 016) as a discount on that cost. Also listens for `Game.Combat.EmberStepUsedEvent` (TASK 011) and applies the ability's cost — a small integrity drain per use, and periodically temporarily forgetting one Optional memory, restored after a delay unless something else changed it first.
- `MemoryPickup` — a fragment in the world. It stays in the scene after collection rather than being destroyed, so a memory cannot be lost to a destroyed object before the grant is recorded. With an optional `SaveIdentity`, marks `WorldObjectState.CollectedFlag` on collection (SPEC.md TASK 009) and restores a remembered collection directly rather than calling `MemoryManager.Discover` again.
- `MemoryEvents` — discovered, state changed, integrity changed.

### Inventory (`Assets/Scripts/Inventory/`)

- `InventoryItem` — one kind of item (ScriptableObject), with the six categories from SPEC.md section 28 (Weapons, Divine Marks, Memory Fragments, Quest Items, Lore, Consumables). Holds only what the UI and `InventoryManager` need — no weight, rarity or equipment slots — section 28's "must be simple, avoid item clutter" in code, not just presentation.
- `InventoryManager` (TASK 016) — a count per item id rather than one entry per physical pickup, scene-scoped like `QuestManager`/`MemoryManager` (see **Manager lookup**) and restored fresh by `SaveManager.Apply` on every scene load. `UseConsumable` heals the player and spends one. Automatically grants a Divine Mark on discovering a Divine-category `MemoryFragment` (SPEC.md Act II's "obtain divine marks"), reacting to `MemoryDiscoveredEvent`'s payload rather than any asset naming a specific god. `startingItems` grants a new game's loadout once at `Awake`; a save's own restore overwrites it, so a returning player never sees it twice. Fills `SaveData.Inventory` (`"itemId:count"` pairs), reserved since the save format was written.
- `ItemPickup` — a generic item in the world, the `InventoryManager` equivalent of `MemoryPickup`. Same optional-`SaveIdentity`/check-now-and-subscribe restore shape as every other TASK 009-style pickup.
- `InventoryEvents` — `InventoryChangedEvent`, so UI does no polling.

### Progression (`Assets/Scripts/Progression/`)

- `SkillDefinition` — one skill-tree node (ScriptableObject): branch (SPEC.md section 30's Warrior/Guardian/Divine/Memory), point cost, an optional prerequisite id, and a `(SkillEffectType, float)` pair rather than a subclass per skill — a new skill is a new asset, not a new class.
- `SkillTreeManager` (TASK 016) — unlocks spend points and are tracked by id; points are an ordinary `WorldState` counter (`SKILL_POINTS`) rather than a new save field, granted on `Game.Quests.QuestCompletedEvent` and `Game.AI.BossDefeatedEvent`. `GetBonus(effectType)` sums every unlocked skill's value for that type — the one query every wired system reads. Scene-scoped and restored by `SaveManager.Apply` the same way `InventoryManager` is; `RestoreUnlocked` fills `SaveData.Abilities` (the unlocked skill ids), reserved since the save format was written, without spending points or firing the live-unlock event.
- `SkillEvents` — `SkillUnlockedEvent` (a live unlock only) and `SkillBonusesChangedEvent` (a live unlock *or* a save restoring a whole set at once — `PlayerProgressionStats` listens for this one specifically so it recomputes correctly either way).
- Of the twelve skills SPEC.md section 30 names, only **four** are read by a system today, one per branch: Warrior's attack damage (`WeaponController`), Guardian's health (`PlayerProgressionStats`/`HealthComponent`), Divine's divine energy (`PlayerProgressionStats`/`DivineEnergyComponent`), and Memory's memory manipulation (`MemoryManager.Corrupt`). The other eight exist as real, unlockable, persisted nodes — cost, prerequisite and display all work — but their effect type is not yet consumed anywhere; see KNOWN_ISSUES.md.

### Save (`Assets/Scripts/Save/`)

- `SaveData` — the whole save, as a plain `[Serializable]` class shaped for `JsonUtility`. It carries every field SPEC.md section 31 names; six of them are reserved and written empty because the systems behind them do not exist. They are there on purpose: the file's shape is what version migration has to reason about, and adding a field later is a migration where filling an existing empty one is not.
- `SaveSerializer` — the file format. A save is an envelope of version, checksum and payload rather than the payload alone, so a truncated or half-written file is detectable without parsing game data out of it. Validation also includes a plausibility pass, which catches a file that parses and checksums correctly but cannot describe a real game.
- `SaveMigration` — brings an older save forward. It has no steps yet; it exists now because the first migration is otherwise written under pressure, with a player's save already broken.
- `SaveStorage` — the four-step replace from SPEC.md section 31, and the corruption rules from section 32. Its root directory is a parameter so tests never touch a player's real save folder.
- `SaveManager` — the aggregator, and the only class allowed to know about every system at once. It also decides when saving is unsafe. `PendingLoad` (static) is set by the Main Menu before a scene loads and consumed by this class's own `Start()` once the destination scene exists, which is how Continue/Load hand a save to a scene the menu never touches. This means `SaveManager` must live on its own GameObject, never one that calls `DontDestroyOnLoad` (see Known Issues) — its `Start()`-once-per-scene-load behaviour depends on being destroyed and recreated fresh by every scene transition. `Apply` also restores the active checkpoint via `CheckpointManager.RestoreActiveCheckpoint` (SPEC.md TASK 009); per-object death and collection state restores itself through `WorldObjectState`'s flags rather than anything `SaveManager` orchestrates directly.
- `SaveBrowser` — read-only queries over save files (`Peek`, `TryFindMostRecent`) for menu UI that has no live game to ask. Free of `MonoBehaviour` and `SaveManager`, so it works before any gameplay scene exists and is testable with no scene at all.
- `ISaveParticipant` — the escape hatch for a system that wants to save something `SaveData` has no field for.

**Why saving is a leaf, not a peer.** SPEC.md section 58 forbids a system depending on every other one. The save system unavoidably has to read them all, so the dependency is made to run one way: `Save` reads `Core`, `Combat`, `Quests` and `Memory`, and none of them reference `Save`. Anything that wants to opt in without being referenced implements `ISaveParticipant` and is found at save time.

**Why restoring is silent.** Applying a save replays no quest, memory or damage events. The player already lived through those beats; re-firing them would set their completion flags and grant their rewards a second time. This is why `QuestProgress.Restore`, `MemoryManager.RestoreState` and `HealthComponent.RestoreTo` exist as separate paths rather than reusing `ReportObjective`, `Discover` and `TakeDamage`.

**Order matters when applying.** World flags go back before quests, because setting a flag publishes an event that quest logic reacts to. Restoring the quests last means their saved status wins over whatever that reaction decided. `SkillTreeManager.RestoreUnlocked` (TASK 016) runs before `RestorePlayer`, for a similar reason: restoring it recomputes the player's max health/energy through `PlayerProgressionStats`, and `RestorePlayer`'s own `HealthComponent.RestoreTo` clamps to whatever max is current when it runs — after would clamp a skilled-up player back down.

### Developer tools (`Assets/Scripts/Debug/`)

SPEC.md section 52's seventeen developer tools (TASK 021). The namespace is
`Game.DevTools`, not `Game.Debug`: a namespace called `Debug` would shadow
`UnityEngine.Debug` for every file in it and the first `Debug.Log` written there
would not compile.

- `DebugMode` — the gate, and two separate questions on purpose. `IsAvailableInThisBuild` is a compile-time constant (`#if UNITY_EDITOR || DEVELOPMENT_BUILD`), so in a release player the branches behind it are dead code the stripper removes — the tools are not hidden from the player, they are not in the binary. Section 52 asks for that, and a runtime flag alone would not deliver it. `IsEnabled` is the developer's own switch inside a build that does have them, and starts off so a stray key in a playtest cannot teleport anyone.
- `DebugCommands` — the twelve state-changing tools as plain statics: no UI, no MonoBehaviour, no scene requirement. That split is the point — a tool that only exists inside an IMGUI window can never be automated, and these are exactly the operations an automated test of a late-game state needs. Each returns the sentence to show rather than logging and returning void, so a failure is answered where the command was typed. They drive the real systems (real events, real flags, real consequences) rather than writing state directly: a debug teleport that skipped the checkpoint system would be testing something the game does not do. `UnlockAbility` walks and pays for the whole prerequisite chain, because a developer asking for a late skill means "put me in the state where I have it".
- `DebugOverlay` — the five read-only readouts (FPS, AI state, navigation, quest flags, save version) as `[Flags] OverlayPanels`. Everything here reads and nothing writes, so a readout can be left up during a playtest with no risk of altering what is being watched. FPS uses `unscaledDeltaTime`, since a readout that says zero while the developer looks at a pause menu is the opposite of useful.
- `DebugConsole` — the IMGUI front end (backquote). Destroys itself in `Awake` in a release build rather than merely hiding, so nothing is left listening for a key in a shipped game. Reads the opening key from the keyboard device rather than an input action, deliberately: the console has to be reachable when the input asset is what is broken, and a developer tool has no business appearing in the player's rebinding screen.

IMGUI for both, rather than a canvas, because they must draw over any scene —
including one whose UI is what is being debugged — and must never need
Inspector wiring to work.

### VFX (`Assets/Scripts/VFX/`)

TASK 018's placeholder pass at SPEC.md section 36 (section 78's placeholder-first rule: primitive geometry and temporary materials rather than stalling on final art). Covers 7 of the 14 listed categories — the ones with an existing real trigger to hang off; water, underwater, lightning, time/dream distortion and wind trails are deferred, since nothing in the game yet has water, a dream sequence or open air worth trailing (KNOWN_ISSUES.md).

- `VfxSpawner` — a static factory, not a system: `Spawn(VfxKind, Vector3)` builds one short-lived `ParticleSystem` from primitive settings (colour, burst count, speed and size per `VfxKind`) on a throwaway GameObject, plays it, and self-destroys once it finishes. Stateless and reference-free, so any system may call it directly — the same class of exception `GameLogger` already is, not a dependency on `VFX` as a system. Uses the `Sprites/Default` shader, which every render pipeline (URP included) ships, so a placeholder particle needs no pipeline-specific material asset.
- `CombatVfx` — a pure `EventBus` listener (`ParryEvent` → spark at the attacker, `GuardBrokenEvent` → dust at the defender, `EmberStepUsedEvent` → divine energy at the player), the same one-way shape `HudUI` already uses: `Combat` never references `VFX`.
- `FireBrazierVfx` — a companion component on the same GameObject as a `FireBrazier`, reacting to its public `Changed` event with a fire burst rather than a change to `FireBrazier` itself, so the puzzle logic stays untouched by a purely cosmetic addition.
- `BossPresentationHooks` — fills `BossController`'s `onPhase3Entered`/`onDefeated` `UnityEvent` hooks (left empty since TASK 013 for exactly this) with a transformation burst, wired once per boss instance in the Inspector rather than the boss framework growing a reference to `VFX`.
- `PuzzleController.Solve` and `MemoryPickup.Interact` each call `VfxSpawner`/`SfxSpawner` (see Audio, below) directly on a live solve/collection — glowing symbols and a memory-fragment burst — never on a save's restore path, the same "cosmetic only on the live event" rule `MemoryPickup`'s own comments already state for its visual toggle. This is `World`/`Memory` calling into a utility, not a dependency on a system; see **Dependencies between systems** below for why that is a different thing from `AI`/`UI` reacting to events.

### Audio (`Assets/Scripts/Audio/`)

TASK 018's placeholder pass at SPEC.md section 40's combat cues. No audio asset exists in the project and none can be authored without external tools, so every clip is generated in code rather than imported — section 78's "placeholder sounds" taken literally. Environmental ambience and music (the rest of section 40) are undone: there is nothing to loop or compose from yet, and a placeholder tone reads as a bug for a texture that is meant to be continuous, unlike a one-shot combat cue.

- `SfxSpawner` — a static factory, `Play(SfxKind, Vector3)`, matching `VfxSpawner`'s shape: a short sine-wave tone with a linear fade-out, generated once per `SfxKind` via `AudioClip.Create`/`SetData` and cached, played from a throwaway `AudioSource` that self-destroys once the clip ends. The same stateless-utility exception `GameLogger`/`VfxSpawner` are.
- `CombatAudio` — a pure `EventBus` listener mirroring `CombatVfx`'s triggers (`DamageAppliedEvent`, `ParryEvent`, `AttackBlockedEvent`, `GuardBrokenEvent`, `EmberStepUsedEvent`), one tone each for weapon impact, parry, block, guard break and divine ability.

### Animation (`Assets/Scripts/Animation/`)

- `PlaceholderAnimator` (TASK 018) — the player's placeholder for SPEC.md section 39's animation list, in the same spirit as `EnemyController.ApplyPhaseTint`/`EnemyCombatant`'s telegraph pulse: a procedural transform tween on a `Body` child rather than a rig's clips, blended with `Quaternion.Slerp` so states change smoothly (section 39's "use animation blending to prevent abrupt transitions") instead of snapping. Reads already-public state it does not own — `WeaponController.IsSwinging` for an attack tilt, `CombatController.IsDodging`/`IsGuarding` for a spin/crouch, `PlayerController.IsSprinting`/`IsGrounded` for a lean, `DamageAppliedEvent`/`PlayerDiedEvent` for a flinch/collapse — and changes none of it. Enemies have no equivalent locomotion cue; their tint and telegraph pulse already cover combat readability, and a second placeholder-animation system for AI was judged lower priority than finishing the player's.

  Deliberately does **not** attempt section 39/ROADMAP TASK 018's literal "attack timings moved to animation events." `WeaponController`/`EnemyCombatant`'s windup/active/recovery durations are read from archetype data and rescaled by `Difficulty` at swing time (see the AI section's "why the state machine is split this way"), not authored into a clip; moving timing authority into real `AnimationEvent`s needs clips whose lengths already match that rescaled duration, which cannot exist without a rig to author them against. Doing it anyway would mean either duplicating the timing data into clips that immediately drift from `Difficulty`, or making clip length the source of truth and losing per-difficulty rescaling entirely — a straight regression, not a placeholder. `PlaceholderAnimator` reads `IsSwinging` to drive a cosmetic tilt instead, keeping the direction of authority exactly where it already was.

## Dependencies between systems

`PlayerController` → `GameLogger` only (no dependency on GameManager for movement).
`PauseMenu` → `GameManager`, `GameLogger`.
`GameManager` → `EventBus`, `GameLogger`. Does not depend on Player/Combat/AI directly.
`Combat` → `Core` (`EventBus`, `GameLogger`) and, in `CombatController`, `PlayerDeath` and `LockOnController` only, `Player.PlayerController` and `Player.PlayerCamera`. `WeaponController` additionally reads `Progression.SkillTreeManager.GetBonus` (TASK 016) — a query, the same class of read `Difficulty.Modifiers` already gets from everywhere, not an event reaction, and documented here as the deliberate exception it is: `Progression` itself sits above `Combat` (it reacts to `Quests`/`AI` events), so this edge is a real cycle in the logical dependency graph, acceptable because the whole runtime is one assembly and the read is one line, not a structural coupling. `LockOnController` additionally reads `Core.SettingsManager.Current.AimAssistEnabled` (TASK 017), the same query-not-event class of exception.
`Player.PlayerCamera` → `Combat` (`CombatEvents.ParryEvent`/`GuardBrokenEvent`, TASK 017), to trigger camera shake — a one-way payload reaction, the same shape `AI` already takes on `Combat.ParryEvent`; `Combat` never references `Player`.

`AI` → `Core` and `Combat`. It does **not** reference `Quests`, `Dialogue` or `Memory`: an enemy that counts towards a quest carries a `QuestTarget`, which belongs to `Quests`. `BossController` additionally reveals a plain `GameObject` reward and exposes `UnityEvent` hooks rather than referencing `UI`, `Memory` or a cinematic system directly — TASK 013's mini-boss reward happens to be a `MemoryPickup`, but `BossController` itself only ever sees it as a `GameObject` to activate.
`World` → `Core`, and `Quests` for reporting objectives and starting quests. `CinematicPlayer` additionally calls `GameManager.EnterCutscene`/`ExitCutscene` (TASK 014) — the one other place outside `PauseMenu` that touches `GameState` directly, both for the same reason: freezing/unfreezing the world is a fact about the whole game, not something each system should poll for itself.
`Dialogue` → `Core` and `World` (for `Interactable`) only. It does **not** reference `Quests` or `Memory`.
`Quests` → `Core`, and reads `Dialogue`'s consequence payload.
`Memory` → `Core`, `Quests`, `Dialogue`'s consequence payload, and — as of TASK 011 — `Combat`'s `EmberStepUsedEvent` payload. This is a deliberate exception, the same shape as `AI` reading `Combat`'s `ParryEvent`: Memory reacts to a published payload, `Combat` never references `Memory`, and the reaction is the exact mechanic SPEC.md section 20 describes ("some divine powers consume memory"). `MemoryManager.Corrupt` additionally reads `Progression.SkillTreeManager.GetBonus` (TASK 016), the same query-not-event exception `WeaponController` above takes.
`Inventory` → `Core`, and reads `Memory`'s `MemoryDiscoveredEvent` payload to grant a Divine Mark — the same one-way-payload shape `Memory` itself uses for `Combat`'s event.
`Progression` → `Core`, and reads `Quests`' `QuestCompletedEvent` and `AI`'s `BossDefeatedEvent` payloads to grant skill points. Nothing in `Progression` is ever referenced back by `Quests` or `AI`.
`Player.PlayerProgressionStats` → `Combat` (`HealthComponent`, `DivineEnergyComponent`, both on the same GameObject) and `Progression` (`SkillTreeManager`, `SkillBonusesChangedEvent`).
`Save` → `Core`, `Combat`, `Quests`, `Memory`, `Inventory`, `Progression` and `Dialogue`'s event payloads. Nothing references `Save`.
`UI` → every content system, read-only, through `EventBus` payloads.

`VFX`/`Audio` → `Core` (`EventBus`), and `Combat`'s event payloads (`CombatVfx`/`CombatAudio`) or a companion component's own host (`FireBrazierVfx`) — the same read-only, one-way shape `UI` already uses. `VfxSpawner`/`SfxSpawner` themselves are stateless utilities with no dependency of their own, the same exception `GameLogger` already is: `World` (`PuzzleController`, `MemoryPickup`) and `AI` (`BossController`, indirectly through `BossPresentationHooks`) call them directly for a cosmetic one-shot, which is calling a utility, not depending on a system — nothing in `VFX`/`Audio` ever calls back into `World` or `AI`. `Animation`'s `PlaceholderAnimator` → `Player` (`PlayerController`) and `Combat` (`CombatController`, `WeaponController`), read-only, on the player's own GameObject; nothing depends on `Animation` in return.

`Core` does not reference `Combat`. `Combat` does not reference `UI`, `VFX`, `Audio` or `Animation`; all four react to combat through `EventBus` payloads or public state instead.

`MainMenuController` (`UI`) → `Core` (`GameSceneManager`, `SettingsManager`, `Difficulty`, `WorldState`) and `Save` (`SaveManager`, `SaveBrowser`). It does not reference Combat, AI, Quests, Dialogue or Memory — a save's data, not this controller, is what a level reads back.

`JournalUI` (`UI`) → `Core` (`GameManager`), `Quests` (`QuestManager`) and `Memory` (`MemoryManager`). It does not reference Combat, AI, Dialogue or Save.
`ProgressionUI` (`UI`) → `Core` (`GameManager`), `Inventory` (`InventoryManager`) and `Progression` (`SkillTreeManager`). It does not reference Combat, AI, Quests, Dialogue, Memory or Save.

### How a conversation changes the world

`PlayerInteractor` → `NpcInteractable.Interact` → `DialogueRunner.Begin` → node shown → consequences applied.

The runner applies flag and relationship consequences itself, because it already depends on `Core`. Quest and memory consequences it **publishes** as `DialogueConsequenceEvent` instead, and `QuestManager` and `MemoryManager` subscribe. This is what keeps Dialogue from referencing every content system at once (SPEC.md section 47): the dependency runs one way, and Dialogue knows nothing about quests or memories.

The one place this is inverted is the memory *gate* on a dialogue node. Dialogue needs to ask "what state is memory X in?", which is a question, not an event. `DialogueGraph.MemoryStateResolver` is a static hook that `MemoryManager` installs on enable; while it is null, memory gates are treated as unsatisfied, so memory-specific lines stay hidden rather than showing wrongly.

### Manager lookup

`WorldState`, `DialogueRunner`, `QuestManager` and `MemoryManager` expose `Instance` through `SceneSingleton.Resolve`, which caches the reference and falls back to a scene search when it is null.

Setting `Instance` in `Awake` alone is not enough. Unity does not guarantee which `Awake` runs first, so a component looking a manager up in its own `Awake` can find null even though the manager is in the same scene; and Unity does not call `Awake` at all in EditMode, which makes such managers untestable. This is the same lesson as `Hitbox` and `Hurtbox` in TASK 002, generalized.

A consequence for tests: because the lookup searches the loaded scenes, EditMode tests that use these managers must run in a scene of their own, or the project's own scene would answer instead. `AvarshaTests` opens an empty scene in `[OneTimeSetUp]` and restores the previous one afterwards.

The one deliberate exception is `CombatController` → `PlayerController.BeginDodge`. A dodge is an impulse that has to be applied through the same `CharacterController.Move` call as ordinary movement, so combat asks locomotion to move rather than moving the player itself. Combat still owns the stamina cost and the invulnerability window. Lock-on follows the same shape: `LockOnController` sets `PlayerController.FacingTarget` and `PlayerCamera.LookTarget`, and neither Player class knows what a target is for.

No system depends on more than one layer below it. Gameplay scripts do not reference story/quest content (SPEC.md section 58, rule 7) — none exists yet in this phase.

**A duplicate singleton destroys itself, never its GameObject.** `GameManager`, `GameSceneManager`, `SettingsManager`, `WorldState` and `CheckpointManager` share a `GameSystems` object with scene-scoped systems (`QuestManager`, `MemoryManager`, `DialogueRunner`). If a duplicate's `Awake` called `Destroy(gameObject)`, revisiting a scene after its persisted original already existed (from an earlier scene) would destroy every sibling component too — silently deleting that scene's quest, memory, dialogue and checkpoint systems along with the duplicate. All five call `Destroy(this)` instead. For the same reason, `SaveManager` never shares a GameObject with anything that calls `DontDestroyOnLoad`: its `PendingLoad` mechanism depends on being destroyed and recreated by every scene load, which a persisted GameObject would prevent.

## Assemblies

Runtime code compiles into `Game.Runtime` (`Assets/Scripts/Game.Runtime.asmdef`) rather than the default `Assembly-CSharp`. This exists so `Assets/Tests/EditMode/` can reference game code: an assembly definition cannot reference the predefined `Assembly-CSharp`, so tests were impossible without it.

Anything driving the Editor by reflection must therefore use `Game.Runtime`, not `Assembly-CSharp`, as the assembly name.

Note that Unity does not call `Awake` on plain MonoBehaviours in EditMode. Components that resolve references must therefore do so lazily rather than only in `Awake`, or they will be unconfigured under test — and, more importantly, also unconfigured at runtime if they are added or reparented after `Awake`. `Hitbox` and `Hurtbox` both resolve on demand for this reason. Components expose a `Configure(...)` method as an explicit test seam where serialized fields need setting.

The split between the two suites is a split of claims, not of convenience. EditMode proves a rule is right: `EnemyController.Decide` is a pure function over a senses snapshot, so the whole transition table is 17 tests with no scene at all. PlayMode proves a system wired into a scene actually obeys that rule — which is a different claim, and the one that was false when TASK 004 first ran.

`TestArena` builds each PlayMode test its own world in code: floor, walls, a NavMesh baked at runtime, actors and manager singletons, all destroyed afterwards. Three things about it are load-bearing. Objects are built inactive and activated last, because in PlayMode `AddComponent` runs `Awake` immediately and a `Configure(...)` call after that is too late. The NavMesh is baked after the ground and before the actors, or an enemy standing on the floor is carved out of the mesh it needs. And `WorldState` is emptied rather than destroyed between tests, because it is `DontDestroyOnLoad` and its `Awake` destroys any duplicate.

The assembly references `Unity.AI.Navigation` where the EditMode one does not, so tests can call `NavMeshSurface.BuildNavMesh()`. Game code needs no such reference: `EnemyNavigator` uses only `UnityEngine.AI.NavMeshAgent`, which is an auto-referenced engine module.

## Working on this project with the Unity CLI

The Unity CLI can drive the open Editor directly, which is how the test scene was built and verified. Scene and asset files should be changed this way rather than by hand-editing `.unity` YAML, because fileIDs and GUIDs are assigned by the Editor and raw edits are invisible to a running Editor until a reimport.

```bash
unity status                                  # confirm an Editor is connected (state "ready")
unity command --project-path <repo>           # list what the Editor exposes
unity command eval_file --file <script.cs>    # run C# against the live Editor
unity command console --level error           # read compile/runtime errors
unity command run_tests --mode editor         # run the EditMode suite
unity command run_tests --mode playmode --async_tests
unity command test_status                     # poll the async run for results
```

PlayMode tests cannot run synchronously over the CLI: entering play mode triggers a
domain reload that drops the request. Start them with `--async_tests` and poll
`test_status` until it reports `completed`.

Two things about `eval_file` that are easy to trip over:

- It compiles against the Editor's current assemblies, so **recompile first** after adding or changing a type, or it will not resolve.
- The file is a **statement body, not a compilation unit**: `using` directives at the top are a syntax error. Write type names fully qualified (`UnityEditor.AssetDatabase`, `Game.Quests.QuestManager`), and use local `System.Func`/`System.Action` variables where a helper method would normally go.
